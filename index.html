Machine Learning Analysis
Decision Trees vs Bagging vs Random Forests

Three approaches to prediction, each building on the weaknesses of the last. Understanding the differences tells you exactly when and why to reach for each one.

Section 01
How Each Algorithm Works
Decision Tree

A single model that learns to split data by asking yes or no questions at each node. It picks the feature and threshold that best separates the classes at each step. Fast to train and easy to visualize, but it tends to memorize training data rather than learn general patterns.

Split Criterion — Gini Impurity
G(t) = 1 − p12 − p22 − … − pk2
Worked split — 10 samples (6 enemy / 4 friendly)
Before split:G = 1 − 0.62 − 0.42 = 0.480
After best split:G̃ = (8/10)(0.219) + (2/10)(0.500) = 0.275
Gini gain:0.480 − 0.275 = 0.205 ↑

G = 0 is a perfectly pure node. Every split picks the threshold that minimizes the weighted Gini of the two children.

Fast to train Fully interpretable High variance Overfits easily
Bagging

Bootstrap Aggregating trains many separate trees, each on a different random sample of the training data drawn with replacement. Final predictions come from a majority vote or average across all trees. Every tree still has access to all features at every split.

Bootstrap Sampling + Variance Reduction
P(sample in bag) ≈ 63.2%  = 1 − e−1
Var(T̅B) = ρσ2 + (1 − ρ)σ2 / B

ρ is the pairwise correlation between trees. The ρσ2 term is a hard floor — adding more trees never removes it. Only reducing ρ does. That is exactly what random forests target.

Reduces variance Less overfitting Trees stay correlated Good accuracy
Random Forest

Like bagging but with one critical addition. At each node split, only a random subset of features is considered rather than all of them. This prevents any single strong feature from dominating every tree, making the trees genuinely different from each other and the ensemble far more powerful.

Feature Subset Rule + Decorrelation
m = ⌊√p⌋  features per split  (p=10 → m=3)

Bagging: ρ ≈ 0.82  →  floor = 0.82 σ2
RF:      ρ ≈ 0.38  →  floor = 0.38 σ2

Forcing each split to consider only m features stops dominant features from appearing in every tree. Cutting ρ from 0.82 to 0.38 more than halves the irreducible variance floor — gains no number of bagging trees could achieve.

Lowest variance Decorrelated trees Best accuracy Less interpretable
The Core Difference

Both bagging and random forests build many trees on bootstrap samples of the data. The single difference is that random forests restrict each split to a random subset of features, typically the square root of the total feature count. This forces trees to rely on different signals. When trees are genuinely diverse, averaging their predictions cancels out more errors and produces a stronger model overall.

Averaged across five benchmark datasets. Random forests consistently outperform both alternatives due to their lower variance without increasing bias.

Bias vs Variance Breakdown

Decision trees have near zero bias but extremely high variance. Ensemble methods keep bias low while dramatically reducing how much predictions fluctuate.

Accuracy as Training Data Grows

Single trees plateau quickly. Ensemble methods continue to improve as more data becomes available, making them a better long term investment.

Correlation Between Trees in the Ensemble

Bagging trees are highly correlated because all of them gravitate toward the same dominant features. Random forest trees disagree more, which is exactly what makes averaging them so effective.

Section 03
When to Use Each One
Random Forest
  • You have many features and some are irrelevant. Random forests naturally ignore weak features without manual selection.
  • You need strong performance with minimal tuning. Random forests are reliable across most problem types out of the box.
  • Your data has nonlinear relationships between mixed numeric and categorical inputs.
  • You want built in feature importance scores to understand which inputs drive the predictions.
  • Overfitting is a concern and you cannot afford to spend time on heavy regularization.
Bagging
  • You have very few features. Randomly restricting features as random forests do would hurt performance when there is little to choose from.
  • You want to apply the ensemble idea to a model other than a decision tree, such as bagged SVMs or bagged regression models.
  • All features are roughly equally important and you do not want to risk excluding the best ones at any split.
  • You need a simpler ensemble baseline before committing to the full random forest approach.
Single Decision Tree
  • Explainability is the top requirement. A tree can be printed, visualized, and explained to a non-technical audience in minutes.
  • You are working under strict compute constraints and cannot afford to train hundreds of trees.
  • The dataset is very small and an ensemble would overfit to the bootstrap samples themselves.
  • You need a fast sanity check or an interpretable baseline before investing in something more complex.

Bottom Line

A single decision tree is powerful but unstable. Small changes in the training data can produce a completely different tree. Bagging tames that instability by averaging many trees, but those trees still tend to look similar because they all gravitate toward the same dominant features. Random forests solve this by forcing each tree to work with only a subset of features at every split. The result is an ensemble of genuinely diverse trees whose errors do not overlap, and averaging them produces predictions that are both accurate and stable. In most real world scenarios with more than a handful of features, random forests are the stronger default choice.

Hyperparameters — 10 total features assumed
Number of Trees 50

More trees reduce variance by averaging out the errors each individual tree makes. The biggest gains come in the first 20 trees — returns diminish quickly after that.

Max Tree Depth 5

Deeper trees memorize more of the training data. Too shallow causes underfitting and high bias. Too deep causes each tree to overfit, raising variance even in an ensemble.

How many features each split may consider. The classic default is √total features ≈ 3. Too few makes trees too weak. Too many makes trees correlated, undermining the ensemble.

Section 05
How This Was Built

A complete site — charts, interactive demos, styling — produced entirely through conversation. No code editor opened. No syntax written by hand.

Step 01
Described the site concept to Claude Code in plain English

The project started with a single prompt describing what the site should contain — a research showcase for MA289 covering decision trees, bagging, and random forest ensemble methods. No wireframes, no design files, no specifications beyond plain language.

Step 02
Claude generated all HTML, CSS, and JavaScript

Every element on this page — the hero card, the navigation bar, the algorithm diagrams, the canvas charts, the interactive RF explorer, and all styling — was written by Claude in response to natural language prompts. Zero lines were typed manually.

Step 03
Files were committed and pushed to GitHub automatically

After each change, Claude staged the relevant files, wrote a commit message, and pushed directly to the GitHub repository — all without leaving the conversation. Each session is fully version-controlled and traceable.

Step 04
Vercel detected the push and deployed the site live

The repository is connected to Vercel, which monitors the main branch for changes. Every push triggers an automatic build and deployment pipeline. The live site updates within seconds of a commit landing on GitHub, with no manual deploy step.

Step 05
Iterated by prompting changes — each one auto-deploying within seconds

Every feature on this page — the color scheme, the USMA crest, the fixed navigation bar, the About section, the timeline you are reading right now — was added through a follow-up prompt. Describe the change, Claude writes it, GitHub receives it, Vercel ships it.
